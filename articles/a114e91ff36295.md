## はじめに

Spannerが[全文検索](https://cloud.google.com/spanner/docs/full-text-search)に対応しました[^1]。この機能の基本的な使い方をまとめます。

[^1]: [2024年10月7日に正式リリース](https://cloud.google.com/spanner/docs/release-notes?hl=ja#October_07_2024)されました。

実際に使う上では、[トークナイザの使い分け](#トークナイザの使い分け)が大きな考慮点になります。

## RDBにおける全文検索とは

リレーショナルデータベース（以下、RDB）は関係モデルに基づいてデータを格納するデータベースです。関係モデルでは正規化によってデータを編成しますが、この正規化の1つとして「[第一正規形](https://ja.wikipedia.org/wiki/%E9%96%A2%E4%BF%82%E3%81%AE%E6%AD%A3%E8%A6%8F%E5%BD%A2)」があります。この正規形ではカラムの値がこれ以上分割できない、つまりスカラー値であることを求めます。正規化された値であれば、RDBはインデックスを作ることでカラムの値に対して完全一致検索を効率よく実行できます。

これに対して、全文検索は文字列や文章の中から部分一致する結果を検索するものです。これをRDBで素直に行うと、たとえば以下のようなクエリが考えられます。

```sql
SELECT id, memo FROM memos WHERE memo like '%keyword%';
```

クエリで使われている `LIKE` 検索の中間一致・部分一致は通常のインデックスでは検索することができず、テーブルフルスキャンが必要となり非常に高コストとなります。このような検索を効率的に行うために全文検索の仕組みがあります。

## Spannerでの全文検索の概要

Spannerでの全文検索は、以下の4ステップに分けて考えます。

- トークナイズ
- インデックス
- クエリ
- スコアリング

### トークナイズ

全文検索における[トークナイズ](https://cloud.google.com/spanner/docs/full-text-search/tokenization)（Tokenize）とは、検索対象の文字列をトークンと呼ばれる単位に分解する操作です。英語の文章を対象にした場合、トークンとは単語とするのが一般的です。英語はスペース区切りで表記するため、スペースや改行で分割する操作で完了する場合が多いです。
トークナイズを行った結果はリストになるため、Spannerではトークンのリスト用に `TOKENLIST` 型が用意されており、トークナイザ関数がこの `TOKENLIST` 型を返します。

英語の文章のトークナイズ例

```text
The quick brown fox jumps over the lazy dog
 => [the,quick,brown,fox,jumps,over,the,lazy,dog]
```

Spannerでは、検索要件や対象データに応じて主に以下の3種類のトークナイザ関数を提供しています。

1. **`TOKENIZE_FULLTEXT`（FULLTEXT）**
   自然言語処理（形態素解析など）を用いて単語単位に分解します。日本語を対象にする場合は `language_tag=>'ja'` を指定します。HTMLタグの除去やタグ位置による重み付けを考慮する `content_type=>'text/html'` も指定可能です。
2. **`TOKENIZE_SUBSTRING`（SUBSTRING）**
   テキストを**単語に分割した上で**、各単語の中から指定した長さの部分文字列（n-gram）を生成します。単語内の部分一致検索（`SEARCH_SUBSTRING`）で利用します。
3. **`TOKENIZE_NGRAMS`（NGRAMS）**
   単語分割を行わず、**文字列全体から**機械的にn-gramを生成します。表記揺れやスペルミスを許容するあいまい検索（`SEARCH_NGRAMS`）で利用します。

三方式でのトークン分解の比較（`TOKENLIST` 型は直接参照できないため、`DEBUG_TOKENLIST` 関数を介して表示しています）：

```sql
-- 1. FULLTEXT（自然言語処理）
spanner> SELECT DEBUG_TOKENLIST(TOKENIZE_FULLTEXT("東京都港区", language_tag=>'ja'));
+------------------------------------------+
|                                          |
+------------------------------------------+
| 東京(boundary), 都, 港, 区(end_boundary) |
+------------------------------------------+

-- 2. SUBSTRING（単語ごとの部分文字列）
spanner> SELECT DEBUG_TOKENLIST(TOKENIZE_SUBSTRING("東京都港区", ngram_size_min=>2, ngram_size_max=>3));
+--------------------------------------------------+
|                                                  |
+--------------------------------------------------+
| [京都, 東京, 港区, 都港], 東京都, 京都港, 都港区 |
+--------------------------------------------------+

-- 3. NGRAMS（文字列全体の連続n-gram）
spanner> SELECT DEBUG_TOKENLIST(TOKENIZE_NGRAMS("東京都港区"));
+------------------------------------------------------------------------------------------+
|                                                                                          |
+------------------------------------------------------------------------------------------+
| [京, 京都, 京都港, 区, 東, 東京, 東京都, 東京都港, 港, 港区, 都, 都港, 都港区], 京都港区 |
+------------------------------------------------------------------------------------------+
```

#### トークナイザの使い分け

3つのトークナイザにはそれぞれトレードオフがあり、ユースケースに応じた使い分けが不可欠です。

| トークナイザ | 分割の仕組み | 主な用途 | 対応クエリ関数 | メリット・特徴 |
| :--- | :--- | :--- | :--- | :--- |
| **FULLTEXT** | 自然言語処理（形態素解析） | 記事本文、レビュー、長文テキスト | `SEARCH` | トークン数が少なくストレージ効率が良い。検索ノイズが少ない。拡張検索（Google検索風の構文）が利用可能 |
| **SUBSTRING** | 単語ごとに分割し、各単語から部分文字列を抽出 | ユーザー名、ニックネーム、商品名、単語内の部分一致 | `SEARCH_SUBSTRING` | 単語内の任意の部分文字列を確実に拾える。`LIKE '%keyword%'` の代替として有用 |
| **NGRAMS** | 単語分割せず、文字列全体から連続n-gramを抽出 | あいまい検索（Fuzzy Search）、人名や表記揺れの検索 | `SEARCH_NGRAMS` | スペルミスや入力揺れがあっても近似マッチで拾い出せる。`SCORE_NGRAMS` による類似度スコアリングが可能 |

選定の指針：

- **文章の意味を重視し、検索ノイズを減らしたい場合（長文向け）** $\rightarrow$ **FULLTEXT**
  レビューや記事本文など、ある程度まとまった日本語文章ではFULLTEXTが最適です。トークンサイズを小さく保ちつつ、関連度スコアリングや高度な検索式が使えます。
- **短いテキストで単語内の部分一致（中間一致）を行いたい場合** $\rightarrow$ **SUBSTRING**
  ユーザー名や商品名など、単語単位での分解が難しく、単語内の一部文字列にマッチさせたい場合に適しています。
- **スペルミスや表記揺れを許容したあいまい検索を行いたい場合** $\rightarrow$ **NGRAMS**
  人名検索や入力補完など、多少の打ち間違いや表記揺れがあっても候補としてヒットさせたい場合に適しています。

#### 実際のテーブルへの適用

Wikipediaの記事タイトルとページビュー数を格納するテーブルを想定します。検索対象のカラム（以下の例では `title`）を全文検索するためには、検索対象とは別のトークンリストを持つカラムを追加します。
トークンリストは検索対象のカラムから[自動生成されるカラム](https://cloud.google.com/spanner/docs/generated-column/how-to?hl=ja)として、また通常のアクセス時に見える必要はないため隠しカラム（`HIDDEN`）として定義します。

```sql
CREATE TABLE articles (
  article_id STRING(36) DEFAULT (GENERATE_UUID()),
  title STRING(MAX),
  views INT64 NOT NULL,
  title_tokens TOKENLIST AS (TOKENIZE_FULLTEXT(title, language_tag=>'ja')) HIDDEN,
) PRIMARY KEY(article_id);
```

`title_tokens` カラムがトークンリストを保持しています。この例では `TOKENIZE_FULLTEXT` をトークナイザとして、検索対象データが日本語であることを指定しています。

### インデックス

トークナイズを行っただけでは効率的な検索を行えないため、実際にはトークンリストに対してインデックスを作成します。
トークンリストを対象にしたインデックスは [`SEARCH INDEX`](https://cloud.google.com/spanner/docs/reference/standard-sql/data-definition-language#create-search-index) という専用のインデックスを使います。

シンプルなインデックス定義例

```sql
CREATE SEARCH INDEX articles_search ON articles(title_tokens);
```

`title` が検索をしたい文字列の入ったカラムですが、`title_tokens` というトークンリストのカラムを対象にしたインデックスであることに注意してください。セカンダリインデックスと同様にインターリーブなども指定可能です。

最終更新時刻や数値カラムで検索結果をソートしたい場合に効率的に検索できるよう、`ORDER BY` 句をインデックスに含めることも可能です（ただし、通常のセカンダリインデックスと異なり `INT64` 型のみサポートされており、`TIMESTAMP` 型でのソートには直接対応していないため、エポックミリ秒などの整数値に変換して保持する必要があります）。
今回の例では各記事のページビュー数のカラムがあるので、このカラムに対して降順で順序付けをしてみます。

```sql
CREATE SEARCH INDEX articles_search ON articles(title_tokens)
ORDER BY views DESC;
```

SEARCH INDEXは全文検索以外にも使うことができ、[セカンダリインデックスではカバーしきれなかった複雑な検索](https://cloud.google.com/spanner/docs/full-text-search/search-vs-secondary-index)でも利用できます。

### クエリ

トークナイザの種類に応じて、対応する検索関数を使ってクエリを発行します。

- **FULLTEXT** $\rightarrow$ [`SEARCH`](https://cloud.google.com/spanner/docs/reference/standard-sql/search_functions#search_fulltext)
- **SUBSTRING** $\rightarrow$ [`SEARCH_SUBSTRING`](https://cloud.google.com/spanner/docs/reference/standard-sql/search_functions#search_substring)
- **NGRAMS** $\rightarrow$ [`SEARCH_NGRAMS`](https://cloud.google.com/spanner/docs/reference/standard-sql/search_functions#search_ngrams)

検索クエリの例（FULLTEXTトークンに対する検索）

```sql
SELECT title, views FROM articles 
WHERE SEARCH(title_tokens, 'ガンダム')
ORDER BY views DESC LIMIT 100;
```

トークナイザがFULLTEXTの場合は拡張検索（`enhance_query=>true`）を有効にすることで、あいまい検索を含む検索が可能になり、Googleでの[Web検索のような高度な検索語指定](https://cloud.google.com/spanner/docs/full-text-search/query-overview?hl=ja#rquery)が行えます。

```sql
-- 「ドラゴン」を含むが「クエスト」は除外する
SELECT title FROM articles 
WHERE SEARCH(title_tokens, 'ドラゴン -クエスト', enhance_query=>true);

-- OR検索やグループ化
SELECT title FROM articles 
WHERE SEARCH(title_tokens, '(東京 オリンピック) OR マラソン', enhance_query=>true);
```

### スコアリング

検索結果を更新日や数値カラムではなく、検索キーワードの出現頻度など関連度（Relevance）が高い順で表示したい場合には、[SCORE関数](https://cloud.google.com/spanner/docs/reference/standard-sql/search_functions#score)を利用します。この関数はTF-IDFのアルゴリズムに基づき計算されたスコア値を返します（NGRAMSの場合は `SCORE_NGRAMS` を使用します）。

```sql
SELECT title, views FROM articles 
WHERE SEARCH(title_tokens, 'ガンダム')
ORDER BY SCORE(title_tokens, 'ガンダム') DESC 
LIMIT 100;
```

記事タイトルよりも長い記事本文などの文章を対象に、適合率の高い順に並べ替えたい場合に有効です。

## まとめ

Spannerでの全文検索機能について紹介しました。RDBでの全文検索機能は [MySQL](https://dev.mysql.com/doc/refman/8.0/ja/fulltext-natural-language.html) や [PostgreSQL](https://www.postgresql.jp/document/16/html/pgtrgm.html) などのRDBにも実装されており、使ったことがある方も多いと思います。
Spannerの全文検索は、用途に応じて **FULLTEXT / SUBSTRING / NGRAMS** という3つのトークナイザを柔軟に選択できる点や、トークナイザとインデックスが明確に分離されている点が特徴的です。自然言語処理ノウハウを活かした拡張検索（FULLTEXT）、単語内部分一致（SUBSTRING）、あいまい検索（NGRAMS）を用途に合わせて適切に使い分けることで、RDB単体で多様な検索要件に対応できます。
