## tl;dr

- SpannerのParameterized Viewsときめ細かいアクセス制御（以下、FGAC）を組み合わせると、共有テーブルのまま1つのViewと1つのデータベースロールでテナント単位の読み取り分離を強制できます。
- アプリケーション側の`WHERE`句の記述漏れによる他テナント参照を防げるほか、AIエージェントが自然言語から生成したSQL（NL2SQL）の参照範囲を特定テナントに限定する用途にも適しています。
- 読み取り（`SELECT`）専用などの制約を押さえつつ、プライマリキーの先頭列にテナントIDを配置してストレージ層へフィルタをプッシュダウンさせる設計が基本になります。

## はじめに

マルチテナントのアプリケーションを設計する際、テナントごとにデータベースやテーブルを分割する方式と、1つのテーブルに複数テナントのデータを同居させる共有テーブル方式があります。

Spannerには1インスタンスあたり100データベース（1ノード以上の場合）、1データベースあたり5,000テーブル・5,000ビュー・100データベースロールという上限があります[^1]。そのため、数百から数万規模のテナントを扱うシステムでは共有テーブル方式を選ぶことになります。

一方で、共有テーブル方式を素直に実装する場合には「すべてのクエリーに漏れなく`WHERE tenant_id = ...`を付与できているか」をアプリケーション側で担保しなければなりません。近年ではAIエージェントが自然言語からSQLを組み立てる（NL2SQL）場面も増えており、意図しない広範なクエリーによって他テナントの行まで参照してしまうリスクはさらに大きな考慮点になります。

本稿では、一般的なリレーショナルデータベース（以下、RDB）の実務経験があり、SpannerでマルチテナントアプリケーションやAIエージェント基盤を設計する方に向けて、[Parameterized Views](https://docs.cloud.google.com/spanner/docs/parameterized-views)[^2]と[FGAC](https://docs.cloud.google.com/spanner/docs/fgac-about)[^3]を組み合わせてデータベース層で読み取り分離を実現する仕組みを整理します。

## Parameterized ViewsとFGACによる読み取り分離の仕組み

マニュアルには、Parameterized Viewsの動作について以下のような説明がされています[^2]。

> Parameterized views use parameters to safely pass application-level context, such as a user ID, to the database. When your application executes a query, it sends the context with the query statement. Spanner accesses this context during execution, but neither the query nor the application user can read or modify it.

言い換えると、SQLの文字列とは別の経路（RPCリクエストのコンテキスト）でテナントIDを渡し、定義者権限（`SQL SECURITY DEFINER`）を持つViewの内部だけで`SECURE_CONTEXT()`関数を通じてその値を取り出し、行を絞り込むイメージです。

ここにFGACを組み合わせ、アプリケーション用のデータベースロール（例: `tenant_reader`）にはViewの`SELECT`権限のみを付与し、ベーステーブルへの権限は一切持たせない構成にします[^2][^4]。これにより、ベーステーブルを直接読むクエリーは拒否され、必ずViewのフィルタを通った行だけが返ります。また、一般ロールのSQLから`SECURE_CONTEXT()`を直接呼び出してもエラーになるため、クエリー側でコンテキスト値を覗き見ることはできません。値はRPCリクエスト単位で渡されるため、単一のクライアント（コネクションプール）を全テナントで共有しても混線しません[^2][^4]。

## 実装の流れ

権限設定とクライアントの呼び出し方が揃わないことには話が始まらないので、DDL定義からGo SDKでのクエリー実行までの最小構成を確認します。

### 準備

共有ベーステーブル（`orders`）と`SQL SECURITY DEFINER`を指定したParameterized View（`secure_orders`）を作成し、アプリケーション用のFGACロールにViewの`SELECT`権限のみを付与します[^2][^4][^8]。

```sql:schema.sql
-- 1. 共有ベーステーブル（先頭キーに tenant_id を配置）
CREATE TABLE orders (
  tenant_id     STRING(36) NOT NULL,
  order_id      STRING(36) NOT NULL,
  amount        INT64 NOT NULL,
  internal_memo STRING(MAX)
) PRIMARY KEY (tenant_id, order_id);

-- 2. DEFINER権限で SECURE_CONTEXT を参照する View を作成
CREATE VIEW secure_orders
SQL SECURITY DEFINER AS
SELECT
  orders.order_id,
  orders.amount
FROM orders
WHERE orders.tenant_id = SECURE_CONTEXT('tenant_id');

-- 3. アプリ用FGACロールを作成し、ViewのSELECT権限のみを付与
CREATE ROLE tenant_reader;
GRANT SELECT ON VIEW secure_orders TO ROLE tenant_reader;
```

Viewの`SELECT`句から`tenant_id`や`internal_memo`を外しておくことで、行レベルの分離と同時に不要な列の隠蔽も行えます。

権限設定では、ベーステーブルへの抜け道が残らないよう2点確認します。データベース側では、全ロールに自動継承される`public`システムロールがベーステーブルの権限を持っていないことを確認します[^2][^4]。IAM側では、アプリケーションの実行サービスアカウントから`roles/spanner.databaseUser`などのデータベースレベルのIAMロールを外し、`roles/spanner.fineGrainedAccessUser`とIAM Conditionsで`tenant_reader`に限定した`roles/spanner.databaseRoleUser`のみを付与します[^5]。

### 実行

Go SDKでは、アプリケーション起動時に`DatabaseRole: "tenant_reader"`を指定して単一の`spanner.Client`を作成し、リクエストごとの`QueryOptions.ClientContext.SecureContext`に認証済みのテナントIDを渡してクエリーを実行します[^4]。

```go:query.go
package main

import (
	"context"
	"fmt"

	"cloud.google.com/go/spanner"
	"cloud.google.com/go/spanner/apiv1/spannerpb"
	"google.golang.org/api/iterator"
	"google.golang.org/protobuf/types/known/structpb"
)

// アプリ起動時に1度作成し、全テナントのリクエストで共有するクライアント
func newTenantClient(ctx context.Context, db string) (*spanner.Client, error) {
	return spanner.NewClientWithConfig(ctx, db, spanner.ClientConfig{
		DatabaseRole: "tenant_reader",
	})
}

// リクエストごとに secure_context を渡して View を検索する
func queryOrders(ctx context.Context, client *spanner.Client, tenantID string) error {
	opts := spanner.QueryOptions{
		ClientContext: &spannerpb.RequestOptions_ClientContext{
			SecureContext: map[string]*structpb.Value{
				"tenant_id": structpb.NewStringValue(tenantID),
			},
		},
	}

	// SQL自体に WHERE 句を書かなくても該当テナントの行だけが返る
	stmt := spanner.Statement{SQL: "SELECT order_id, amount FROM secure_orders"}
	iter := client.Single().QueryWithOptions(ctx, stmt, opts)
	defer iter.Stop()

	for {
		row, err := iter.Next()
		if err == iterator.Done {
			break
		}
		if err != nil {
			return err
		}
		var orderID string
		var amount int64
		if err := row.Columns(&orderID, &amount); err != nil {
			return err
		}
		fmt.Printf("order_id=%s, amount=%d\n", orderID, amount)
	}
	return nil
}
```

このクライアントから直接`SELECT * FROM orders`を実行すると権限エラーになり、AIエージェントが`SELECT * FROM secure_orders`のような全体取得クエリーを生成した場合でも、`opts`で渡したテナントの行しか返りません。

## 先頭キー設計によるストレージ層へのプッシュダウン

Parameterized Viewsは1つのView定義を全テナントで使い回せるため、テナント数が増えても5,000ビューの上限を圧迫しません。一方で、共有テーブルのデータ量が増えても高速に読み取れるようにするには、プライマリキー（またはセカンダリインデックス）の先頭列に`tenant_id`を配置する設計が欠かせません[^2]。

Spannerはプライマリキーの昇順にデータを並べて格納します[^6]。そのため、`tenant_id`が先頭キーにあれば、`WHERE orders.tenant_id = SECURE_CONTEXT('tenant_id')`の条件がストレージ層へプッシュダウンされ、該当テナントの連続したキー範囲だけを直接スキャンできます[^2]。なお、特定ノードへの負荷集中（ホットスポット）を避けるため、`tenant_id`や`order_id`には連番ではなくUUIDv4などのばらつきのある値を使用します[^6]。

## 導入時に押さえておきたい制約と境界

Parameterized Viewsは共有テーブルの読み取り分離を簡潔に実装できますが、書き込み制御や周辺APIまですべてを代替する機能ではありません。実務で採用する際は、以下の制約と責任分界点を押さえて設計します[^2][^7]。

| 観点 | 仕様・制約 | 設計時の対応 |
| :--- | :--- | :--- |
| 読み取り専用（DML非対応） | Viewに対する`INSERT`・`UPDATE`・`DELETE`は実行できません[^7]。 | 更新処理は別ロールまたは信頼されたバックエンド処理に分離し、アプリケーション層で`tenant_id`の付与・検証を強制します。 |
| 非対応APIとクエリーモード | キー指定のRead APIとSpanner Data Boostは利用できません。またベーステーブル権限を持たないロールでは`NORMAL`以外のクエリーモードがエラーになります[^7]。 | SQL実行API（`ExecuteSql` / `ExecuteStreamingSql`）を使い、実行計画やプロファイルの確認（`PLAN` / `PROFILE`モード）はベーステーブル権限を持つロールで行います[^7]。 |
| `SECURE_CONTEXT()`の型と利用箇所 | 引数は文字列リテラル必須で、戻り値は常に`STRING`型です。生成列・デフォルト値式・UDF内部では呼び出せません[^2]。 | 数値列との比較には`CAST(SECURE_CONTEXT('id') AS INT64)`を使います。複数属性を渡す場合はJSON文字列を1キーに入れ、View側でJSON関数を使って抽出します[^2]。 |
| コンテキストの信頼境界 | Spannerは渡された`secure_context`の値をそのまま評価します。 | クライアントからの未検証入力を直接渡さず、バックエンドで認証・認可を済ませたテナントIDを設定します。 |
| 任意SQL・NL2SQL時の多層防御 | View外の式（ゼロ除算など）がフィルタより先に評価される場合があり（Security Barrier非搭載）、エラー有無からデータ存在を推測される余地があります[^2][^7]。 | ユーザー入力をもとにLLMでSQLを生成する場合は、[Model Armor](https://cloud.google.com/security/products/model-armor)によるプロンプトインジェクション対策やクエリーのテンプレート化を併用します[^2]。 |

## まとめ

SpannerのParameterized ViewsとFGACを組み合わせると、共有テーブルのまま1つのView定義と単一の`spanner.Client`（データベースロール）で、リクエスト単位のテナント読み取り分離をデータベース層に強制できます。アプリケーションの`WHERE`句漏れ対策だけでなく、NL2SQLのように動的なクエリーを実行するAIエージェント基盤のガードレールとしても扱いやすい仕組みです。

プライマリキー先頭列への`tenant_id`配置によるプッシュダウン設計と、読み取り専用・非対応APIなどの制約を確認の上で、マルチテナント設計の選択肢としてご活用ください。
