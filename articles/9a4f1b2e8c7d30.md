## tl;dr

- Cloud Spannerにおいて、大量のトラフィックが予想されるリリース前にテーブルやインデックスを事前分割（Pre-splitting）するためのSplit Point API（`AddSplitPoints`）が提供されています。
- これまでは負荷試験ツールなどでアクセスを発生させてスプリット分割を促す方法がありましたが、Split Point APIを使うことで、空のテーブルに対してCLIやAPIから境界キーを指定するだけで事前分割を行えます。
- 事前分割したスプリットには有効期限（デフォルト10日、最大30日）があり、期限後は再びCloud Spannerによる自動管理へ移行します。

## はじめに

以前執筆した記事[「ツールを使ったCloud Spannerのウォームアップ」](https://zenn.dev/google_cloud_jp/articles/1adfdfc1fa5a6c)では、大規模なサービスローンチやイベントに備えてCloud Spannerのテーブルを事前に分割しておくウォームアップ（暖機運転）の方法として、[gcsb](https://github.com/cloudspannerecosystem/gcsb)という負荷試験ツールを使う手順を紹介しました。

Cloud Spannerはデータサイズやアクセス負荷に応じて自動的にテーブルを複数のスプリットへ分割しますが、分割処理そのものには数分程度の時間がかかります。そのため、テーブル作成直後のスプリットが1つしかない状態でいきなり大量のリクエストが到来すると、単一のノードに処理が集中してリクエストキューが滞留し、テールレイテンシ（99パーセンタイルなどの高いパーセンタイルのレスポンス時間）が増加する要因となります。

これに対して、従来は本番相当のキー範囲でデータを書き込み、継続してアクセス負荷をかけることで事前にスプリット分割を促す運用が行われてきました。その後、Cloud Spannerにスプリットの境界（Split Point）を直接指定して事前分割を行えるSplit Point API（`AddSplitPoints`）[1]が実装されました。

本稿では、まず事前分割の全体像とスプリット管理の仕組みを整理した上で、Split Point APIを使ってテーブルやインデックスを事前分割する具体的な手順を解説します。

## 事前分割（Pre-splitting）の全体像と仕組み

具体的なコマンド手順に入る前に、Cloud Spannerにおけるスプリット分割の役割と、なぜSplit Point APIに有効期限という概念があるのかという大枠を整理します。

### 一般的なRDBとの違いと事前分割の役割

一般的なリレーショナルデータベース（以下、RDB）では、単一のサーバーインスタンス内のストレージ領域にデータが格納されるため、リリース前に空のテーブルを分割しておくといった作業は通常発生しません。一方で、分散データベースであるCloud Spannerでは、プライマリキーの辞書順でデータをソートし、そのキー範囲をスプリット（Split）と呼ばれる単位に分割して複数のノードへ分散配置します。

マニュアルには事前分割（Pre-splitting）について、以下のような説明がされています[2]。

> By pre-splitting the database, Spanner can be ready for a predictable increased traffic. You can pre-split your database by creating split points.

あらかじめプライマリキーの境界値（Split Point）を登録しておくことで、データが1件も入っていない空のテーブルであっても複数のスプリットへ分割し、各ノードへ均等に配置させておくイメージです。言い換えると、負荷による自動分割が発動するのを待たずに、最初からスケールアウトした状態でトラフィックを迎え撃つ動作とも言えます。

ウォームアップなし（自動分割のみ）、負荷試験ツールによるウォームアップ（`gcsb`）、およびSplit Point APIの3つのアプローチで、リリース前後のスプリット配置とレイテンシがどのように推移するかを比較したものが以下のアニメーションです。

![ウォームアップ手法ごとのスプリット配置とレイテンシ推移の比較](/images/split_point_animation.gif)

ウォームアップを行わない場合は、サービスイン直後（`T=0分`）にNode 1の単一スプリットへすべてのアクセスが集中し、CPU使用率が上昇してp99レイテンシが悪化します。これに対して事前に分割を行っておいた場合は、サービスインの瞬間から各ノードへリクエストが分散され、安定した低レイテンシを維持できます。

### 有効期限（Expiration time）がある理由

Split Point APIを使う上で特徴的な仕様として、追加したスプリットには必ず有効期限（Expiration time）が設定されるという点があります。有効期限はデフォルトで作成・更新から10日後となっており、最大で30日後まで指定できます。

なぜ手動で作ったスプリットが永続化されず、一定期間で有効期限を迎える仕様になっているのか、データベースエンジンの実装者の気持ちになって考えてみるとその理由が理解しやすいと思います。

Cloud Spannerにおいてスプリットの数が増えるということは、管理すべきPaxosグループ（レプリケーションの合意形成単位）が増えることを意味します。アクセスが集中している間はスプリットが細かく分かれている方が並列度が高まり有利ですが、たとえば発売記念キャンペーンやイベントが終了してトラフィックが平常時の水準に落ち着いたあとも大量の空スプリットが残り続けると、以下のようなオーバーヘッドが発生します。

- 複数キーにまたがる読み取りやフルスキャンを実行する際、アクセス対象となるスプリットの数が増え、ネットワーク通信およびクエリーの集約コストが増加する
- 複数のスプリットにまたがる書き込みトランザクションにおいて、2相コミット（2PC）の参加者（Participants）が増え、トランザクションのレイテンシやメモリ消費量が増加する

そのため、キャンペーンやリリース直後のピークを乗り切ったあとは、人間が指定した分割境界を解除し、Cloud Spanner本来の「負荷とサイズに応じた動的な分割・統合（マージ）管理」へ制御を戻す必要があります。これが、Split Point APIに有効期限が設けられている理由です。有効期限が過ぎたスプリットは自動的にシステム管理下へ移行し、トラフィックが少ない状態が継続すればCloud Spannerによって適切にマージされます。

## 準備

ここからは具体的な手順に入ります。以前の記事と同様に`Singers`テーブルと、そのセカンダリインデックスである`SingersByFirstLastName`を題材に事前分割の手順を確認します。まずは操作の対象となるテーブルとインデックスが定義されている状態から始めます。

```sql
CREATE TABLE Singers (
  SingerId   STRING(36) NOT NULL,
  FirstName  STRING(1024),
  LastName   STRING(1024),
  SingerInfo BYTES(MAX)
) PRIMARY KEY (SingerId);

CREATE INDEX SingersByFirstLastName ON Singers(FirstName, LastName);
```

事前分割を実行するには、対象のインスタンスに十分な計算容量（ノード数またはProcessing Units）が割り当てられている必要があります。公式ドキュメントでは、1ノードあたり10個程度のSplit Pointを作成することが推奨されています[2]。なお、小規模なインスタンスでは負荷に応じた自動分割が素早く追従するため、事前分割は主に数ノード以上の規模で急激なトラフィック増加が見込まれる場面で効果を発揮します。

また、操作を実行するIAMユーザーまたはサービスアカウントには、`spanner.databases.addSplitPoints`権限（`roles/spanner.databaseAdmin`ロールなどに含まれます）が必要です。

### スプリット定義ファイルの作成

`gcloud`コマンドからSplit Pointを追加する場合、分割したい境界キーをテキストファイル（1行につき1つの境界）として記述します。1回のAPIリクエスト（1ファイル）で指定できる上限は100個までです。

記述フォーマットは以下の通りです[1]。

```text
ObjectType ObjectName (SplitValue1, SplitValue2, ...)
ObjectType ObjectName (IndexSplitValue1, ...) TableKey (TableSplitValue1, ...)
```

- `ObjectType`: 分割対象のオブジェクト種別として`TABLE`または`INDEX`を指定します。
- `ObjectName`: 対象のテーブル名またはインデックス名を指定します。
- `SplitValue`: プライマリキーまたはインデックスキーの境界値をカンマ区切りで指定します。

値を記述する際の主なルールは以下の通りです。
- 文字列（`STRING`）、タイムスタンプ（`TIMESTAMP`）、および整数（`INT64`）・数値（`NUMERIC`）はシングルクォート`'`で囲みます（例: `'123'`, `'2026-09-17T00:00:00Z'`）。
- 浮動小数点数（`FLOAT64`）や真偽値（`BOOL`）はシングルクォートで囲まずに記述します（例: `1.287`, `true`）。
- 複合キーの場合、プライマリキーの先頭カラムからのプレフィックス（前方一致部分）だけを指定することも可能です。

たとえば、`SingerId`にUUIDv4（`STRING(36)`）を使用しており、16進数の文字空間（`0`〜`f`）を4分割したい場合、およびセカンダリインデックス`SingersByFirstLastName`を名前のアルファベット順で分割したい場合は、以下のような`splits.txt`を用意します。

```text
TABLE Singers ('40000000-0000-0000-0000-000000000000')
TABLE Singers ('80000000-0000-0000-0000-000000000000')
TABLE Singers ('c0000000-0000-0000-0000-000000000000')
INDEX SingersByFirstLastName ('G', 'A')
INDEX SingersByFirstLastName ('N', 'A')
INDEX SingersByFirstLastName ('T', 'A')
```

セカンダリインデックスは内部的には「インデックスキー＋ベーステーブルの主キー」を主キーとする別のテーブルとして実装されています。そのため、特定のインデックスキーに大量のレコードが集中することが分かっている場合は、`TableKey`オプションを併用してベーステーブルの主キー（`SingerId`）まで含めた境界を指定することで、同一インデックスキー内をさらに細かく分割することもできます。

```text
INDEX SingersByFirstLastName ('Smith', 'John') TableKey ('80000000-0000-0000-0000-000000000000')
```

## 実行

定義ファイルが準備できたら、`gcloud spanner databases splits add`コマンドを実行してデータベースへ適用します。

```sh
gcloud spanner databases splits add sample-database \
  --instance=sample-instance \
  --splits-file=splits.txt \
  --initiator="launch-prep-2026" \
  --split-expiration-date="2026-09-30T00:00:00Z"
```

各オプションの意味は以下の通りです。
- `--splits-file`: 先ほど作成したスプリット定義ファイルのパスを指定します。
- `--initiator`: 誰が・何の目的で追加したスプリットかを識別するための任意のタグ文字列です（省略可能）。
- `--split-expiration-date`: スプリットの有効期限をISO 8601形式（UTC）で指定します（省略時は実行時刻から10日後）。

なお、Split Pointを追加してからバックグラウンドでの分割・ノード間再配置が完全に落ち着くまでには少し時間がかかります。そのため、公式のベストプラクティスではトラフィック増加が見込まれる時刻の7日前から12時間前までの間にこのコマンドを実行しておくことが推奨されています[2]。

### 分割状態の確認

追加したSplit Pointが正しく認識されているかは、`gcloud`コマンドまたはシステムテーブル（`SPANNER_SYS`）へのクエリーから確認できます。

CLIから一覧を取得する場合は以下のコマンドを実行します。

```sh
gcloud spanner databases splits list sample-database \
  --instance=sample-instance
```

Spanner Studioや`spanner-cli`からSQLで確認する場合は、`SPANNER_SYS.USER_SPLIT_POINTS`ビューを参照します。

```sql
SELECT
  TABLE_NAME,
  INDEX_NAME,
  INITIATOR,
  SPLIT_KEY,
  EXPIRE_TIME
FROM SPANNER_SYS.USER_SPLIT_POINTS;
```

実行すると、以下のように登録したスプリット境界と有効期限の一覧が得られます。

```text
+------------+------------------------+------------------+-----------------------------------------------+----------------------+
| TABLE_NAME | INDEX_NAME             | INITIATOR        | SPLIT_KEY                                     | EXPIRE_TIME          |
+------------+------------------------+------------------+-----------------------------------------------+----------------------+
| Singers    |                        | launch-prep-2026 | Singers('40000000-0000-0000-0000-000000000000')| 2026-09-30T00:00:00Z |
| Singers    |                        | launch-prep-2026 | Singers('80000000-0000-0000-0000-000000000000')| 2026-09-30T00:00:00Z |
| Singers    |                        | launch-prep-2026 | Singers('c0000000-0000-0000-0000-000000000000')| 2026-09-30T00:00:00Z |
| Singers    | SingersByFirstLastName | launch-prep-2026 | Index: SingersByFirstLastName on Singers...   | 2026-09-30T00:00:00Z |
+------------+------------------------+------------------+-----------------------------------------------+----------------------+
```

また、以前の記事で紹介した「クエリーの実行プランにおけるテーブルスキャン実行数（`Executions`）から分割数を確認する方法」も引き続きそのまま利用できます。データが空の状態であっても、フルスキャンを強制するヒント句をつけて`EXPLAIN ANALYZE`を実行すると、`Table Scan`や`Index Scan`の`Executions`が分割数に応じて増えていることが確認できます。

```sql
EXPLAIN ANALYZE SELECT count(*) FROM Singers@{FORCE_INDEX=_BASE_TABLE};
```

一覧をみて、データを書き込むことなくテーブルとインデックスの事前分割が完了しているなと実感いただけるのではないかと思います。

## 片付け（有効期限の変更と即時削除）

Split Point APIによる事前分割ではダミーデータが存在しないため、サービスインにあたってのデータ削除作業は不要です。指定した有効期限が到来すれば自動的にシステム管理へ戻るため、基本的にはそのまま運用を開始できます。

ただし、以下の場面では手動でSplit Pointの有効期限を変更（または即時失効）させる操作が必要になります。

1. イベント期間が延長され、有効期限を延ばしたい場合:
   同じ`splits.txt`を指定して、新しい`--split-expiration-date`（現在時刻から最大30日以内）で再度`gcloud spanner databases splits add`を実行することで、有効期限を上書き延長できます。
2. テーブルやインデックスを削除（`DROP TABLE` / `DROP INDEX`）したい場合:
   ここが運用上の考慮点になりますが、有効なSplit Pointが残っているテーブルやインデックスを削除する場合、事前にそれらのSplit Pointを失効（Expire）させておく必要があります[2]。これを行わずに削除すると、インスタンスレベルのSplit Point割り当て上限（クォータ）が解放されないためです。

登録済みのSplit Pointを即座に失効させるには、`--split-expiration-date`に現在時刻（または現在時刻より少し前の時刻）を指定して`splits add`コマンドを再実行します。

```sh
# 現在時刻を指定して即座にSplit Pointを失効させる例
gcloud spanner databases splits add sample-database \
  --instance=sample-instance \
  --splits-file=splits.txt \
  --split-expiration-date="$(date -u +%Y-%m-%dT%H:%M:%SZ)"
```

実行後、`SPANNER_SYS.USER_SPLIT_POINTS`から対象のエントリが消えたことを確認した上で、`DROP TABLE`などを実行してください。

## よくある（かもしれない）疑問点

### 負荷試験ツール（gcsbなど）によるウォームアップはどう使い分けるか？

「リリース前にテーブルやインデックスをあらかじめ分割しておきたい」という目的だけであれば、Split Point APIを使うことで手軽に事前分割が完了します。

一方で、実際のアプリケーションが発行するJOINクエリーやトランザクション処理を含めて、「本番想定の秒間リクエスト数（QPS）を流したときにCPU使用率やレイテンシがどうなるか」をE2Eで検証・ベンチマークしたい場面では、引き続き`gcsb`やアプリケーション独自の負荷試験ツールによるテストが有効です。つまり、スプリットの事前分割にはSplit Point APIを使い、性能限界やクエリーの検証には負荷試験ツールを使う、という形で役割を分けて活用すると良いでしょう。

### インターリーブされたテーブルはどう扱えばよいか？

親子関係を持つインターリーブテーブル（`INTERLEAVE IN PARENT`）の場合、親テーブルにSplit Pointを追加すると、同じ主キープレフィックスを持つ子テーブルのデータも同じ境界で一緒に分割されます。もし特定の子テーブルに対して親テーブル以上に偏ったアクセスが予想される場合は、子テーブルの複合主キー（親キー＋子キー）を指定して個別にSplit Pointを追加することも可能です。

### 全文検索インデックスやベクトルインデックスも分割できるか？

現時点の制限事項として、全文検索インデックス（Search Index）およびベクトルインデックス（Vector Index）に対して直接Split Pointを指定することはできません[2]。これらを利用している場合は、ベーステーブルに対して事前分割を行ってください。

## まとめ

Split Point API（`AddSplitPoints`）により、Cloud Spannerにおけるリリース前の事前分割作業は定義ファイルの投入によってシンプルに行えるようになりました。

- 急激なトラフィック増加が見込まれる7日前〜12時間前に`gcloud spanner databases splits add`で境界キーを登録する
- 1ノードあたり10個程度のSplit Pointを目安とし、必要に応じてセカンダリインデックスにも設定する
- 有効期限（デフォルト10日）で自動的にシステム管理へ戻るが、テーブル削除前には現在時刻を指定して明示的に失効させる

これらの特徴を理解することで、大規模なリリースやイベント時にもテールレイテンシの悪化を防ぎ、Cloud Spannerの性能を最初から効果的に引き出すことができます。制限事項やクォータなどを確認の上でご活用ください。
