## tl;dr

- Spannerでは一般的なRDBと異なり、トランザクションを識別する論理的な「セッション」と、通信を行う「gRPCチャネル（HTTP/2コネクション）」が独立した層に分かれています。
- 現在は主要なクライアントライブラリでMultiplexed Sessionsがデフォルト有効になったため、かつて必要だったセッションプールのサイズ設計やKeep-Alive、セッションリークによるプール枯渇への対策は原則不要になりました。
- 一方で、1本のgRPCチャネルあたり最大100並行リクエストというHTTP/2層の制約や、Dynamic Channel Pooling（負荷に応じたチャネル数の自動調整）などの対応状況には言語ごとの差があるため、現在の構成に合わせたポイントを押さえておく必要があります。

## はじめに

アプリケーションからデータベースを使う際、接続されないことには話が始まらないので、まずはコネクション周りの設計を確認することが多いと思います。

しかし、Spannerの接続周りを調べると、セッション、セッションプール、gRPCチャネル、HTTP/2ストリームといった用語が並び、一般的なリレーショナルデータベース（以下、RDB）とは勝手が違って戸惑う場面が少なくありません。さらにWeb上の技術記事でも、執筆された時期によって「同時実行数に合わせてセッションプールを設計し、Keep-Aliveで維持する必要がある」と書かれていたり、「セッションの設定は不要である」と書かれていたりと、過去の定石と現在の仕様が混在して見えにくい状態にあります。

本稿では、RDBの経験がある方や数年前のSpannerの知識をお持ちの方に向けて、Spannerの接続構成が過去から現在にかけてどのように変わったのかを、近年のセッション管理やgRPCチャネル周りの機能進化を中心に図解で整理します。なお、説明をシンプルにするため、本稿では公式クライアントライブラリ（Go、Java、Node.js、Python、Ruby、PHPの6言語）を直接利用する構成に対象を絞り、JDBCや`database/sql`、PGAdapterなどの互換ドライバー層は扱いません。

## 一般的なRDBとSpannerの接続モデルの違い

最初に、なぜSpannerにはRDBのような単一の「コネクションプール」ではなく、セッションとgRPCチャネルという2つの概念が登場するのかを整理します。

MySQLやPostgreSQLなどの一般的なRDBでは、アプリケーションがデータベースサーバーへ張る「1本のTCPコネクション」と「1つのデータベースセッション」、そしてその上で動く「1つの実行中トランザクション」が原則として1対1で結びついています。たとえば同時に200個のトランザクションを実行したい場合は、コネクションプールに200本のTCP接続を用意して順番に貸し出すというシンプルな対応関係になります。

一方で、SpannerではクライアントライブラリがSpanner APIフロントエンド（以下、AFE）に対して、TLSで暗号化されたHTTP/2上のgRPCを用いて通信します。この構成では、RDBでは一体になっていた役割が「セッション」と「gRPCチャネル」という独立した2つの層に切り離されています。

まず、AFE側でトランザクションの実行コンテキストを識別するための論理的なIDが「セッション（Session）」であり、これはTCP接続そのものではありません。次に、実際にネットワーク越しにリクエストを送受信する持続的なTCP/TLS（HTTP/2）コネクションが「gRPCチャネル」であり、HTTP/2のストリーム多重化によって1本の接続に複数のリクエストを同時に流せます。

## セッション層の変遷：セッションプールからMultiplexed Sessionsへ

### 過去の構成（Regular Sessions）

従来のRegular Sessionsには「1つのセッション上で同時に1つのトランザクションしか実行できない」という制約がありました。リクエストのたびにセッションを新規作成すると往復のレイテンシがかかるため、クライアントライブラリ内部に「セッションプール」を持ち、あらかじめ作成しておいたセッションを貸し借りして再利用する構成が採られていました。

その結果、同時実行数に合わせたプールサイズ（`MinSessions` / `MaxSessions`）の見積もりや起動時のウォームアップ、アイドル切断を防ぐ定期的なKeep-Alive（`SELECT 1`）、さらに返却漏れ（セッションリーク）によるプール枯渇への対策など、開発者が意識すべき管理項目が多くありました。

### 現在の標準構成（Multiplexed Sessions）

こうしたセッションプールの管理コストを解消するために導入されたのが、[Multiplexed Sessions](https://docs.cloud.google.com/spanner/docs/sessions#multiplexed_sessions)（マルチプレックスセッション）です。1つのセッション識別子をすべてのgRPCチャネル横断で共有し、その単一のセッション上で多数のトランザクションを同時に実行できる仕組みになっています。

2024年7月の一般提供（GA）以降、当初は環境変数によるオプトイン形式で提供され、対応範囲も読み取り専用（Read-Only）トランザクションから段階的に拡大されてきました。現在は単発の読み書き・Read-Onlyトランザクション・Partitioned DMLなどのパーティション操作・Read-Writeトランザクションのすべてに対応しており、後述する主要6言語すべてのクライアントライブラリで設定不要のデフォルト有効へと切り替わっています。

Multiplexed Sessionsが標準になったことで、従来の考慮点は以下のように変わりました。

#### セッションプール設計とウォームアップの不要化

1つのMultiplexed Sessionで任意の並行数のトランザクションを同時に処理できるため、`MinSessions`や`MaxSessions`の見積もり、および起動時やスケールアウト時の大量セッション作成が不要になりました。

#### セッションリークによるプール枯渇の解消

リクエストごとに個別のセッションを貸し出す仕組みではなくなったため、セッション返却漏れによってプール全体が枯渇し、後続のリクエストまでブロックされる事象がなくなりました。なお、セッションプールの枯渇は起きなくなったものの、読み取り結果のストリームやトランザクション自体を閉じ忘れるとHTTP/2ストリーム枠やサーバー側のロックを占有してしまうため、使い終わったリソースを適切にクローズする実装は引き続き必要です。

#### Keep-Aliveの不要化と自動ローテーション

アイドル状態が続いても維持用のクエリーを流す必要はなく、古いセッションへの送信を防ぐためにクライアントライブラリが7日ごとに自動で新しいセッションへローテーションします。バックエンド側でもセッション所有権の維持やガベージコレクションに伴う負荷が削減されます。

#### チャネル紐付けの不要化と稼働状況の確認

単一のセッション識別子をどのgRPCチャネルに流してもよくなったため、チャネル間の負荷分散や設定のカスタマイズがシンプルになりました。既存のアプリケーションがRegular SessionsとMultiplexed Sessionsのどちらで通信しているかは、Cloud MonitoringのMetrics ExplorerにてOpenTelemetryクライアントメトリクス（`Spanner/num_acquired_sessions`など）の`is_multiplexed`フィルタを見ることで判別できます。

## gRPCチャネル層：HTTP/2ストリームとチャネルプール

Multiplexed Sessionsによって「セッション数の上限」は意識しなくてよくなりましたが、実際にネットワーク上でRPCを送受信する通信層であるgRPCチャネルの物理的な制約はそのまま残っています。現在のSpanner接続において実質的な「コネクションプール」にあたるのが、このgRPCチャネルのプールです。

### 1本のgRPCチャネルで処理できる並行数

1本のgRPCチャネルはおおむね1本の持続的なTCP/TLS（HTTP/2）コネクションに相当します。HTTP/2では1本のTCP接続の中に複数の仮想的な「ストリーム（Stream）」を作ることで複数のリクエストを同時にやり取りできますが、Spannerにおける1本のgRPCチャネルが同時に処理できるリクエスト数は最大100並行までとなっています。

そのため、1つのアプリケーションインスタンスから同時に100を超えるリクエストを実行する場合、gRPCチャネルが1本しかないとHTTP/2ストリームの空き待ち（チャネル混雑）が発生し、p95やp99といったテールレイテンシが悪化する原因になります。これを防ぐため、GoやJavaなどのクライアントライブラリでは起動時に複数本のgRPCチャネル（たとえばGoの標準では4本＝最大400並行相当）を作成してプールしています。

### 固定チャネルプールとDynamic Channel Pooling

従来は、初期の固定チャネル数を超える高スループットなアプリケーションを運用する場合、「最大並行リクエスト数 ÷ 100」を目安として開発者が手動で固定チャネル数を増やす必要がありました。一方で、最初から大量のチャネルを固定で張るとアイドル時もTCP接続やメモリを消費し続け、逆に少なすぎるとピーク時にチャネル混雑が起きるというトレードオフがありました。

このチャネル数の管理を自動化するため、Node.jsクライアントで先行導入されていた[Dynamic Channel Pooling](https://docs.cloud.google.com/spanner/docs/sessions#configure_the_number_of_sessions_and_grpc_channels_in_the_pools)（動的チャネルプール、以下、DCP）が、2026年8月にGoとJavaのクライアントライブラリでも一般提供（GA）となりました。

GoおよびJavaでDCPを有効化（オプトイン）した場合、標準では初期4チャネル（最小2〜最大10チャネル）で起動します。負荷が増えて1チャネルあたりの並行RPC数が上限閾値（標準では25並行）を超えると、イベント駆動で即座に新しいgRPCチャネルが追加されます。反対に負荷が落ち着いた場合は、3分間隔の定期チェックにおいて1チャネルあたりの並行RPC数が下限閾値（標準では15並行）を下回り続けているチャネルが閉じられます。

## 主要6言語のクライアントライブラリ対応状況

ここまで見てきた「Multiplexed Sessions」と「gRPCチャネルプール（およびDCP）」は、どのプログラミング言語のクライアントライブラリでも同じように揃っているわけではありません。2026年11月時点の公式仕様に基づき、Webアプリケーション開発でよく使われる6言語の実装状況を比較すると以下の通りです。

| 言語 | Multiplexed Sessions | 標準のgRPCチャネル構成 | Dynamic Channel Pooling |
| :--- | :--- | :--- | :--- |
| Go | デフォルト有効（`v1.85.0`以降） | 固定4チャネル | 対応（`v1.92.0`以降 / オプトイン） |
| Java | デフォルト有効（`v6.98.0`以降） | 固定8チャネル（`v6.104`以前は4） | 対応（`v6.105.0`以降 / オプトイン） |
| Node.js | デフォルト有効（`v8.3.0`以降） | DCP標準（最大10チャネル） | デフォルト有効 |
| Python | デフォルト有効（`v3.57.0`以降） | 単一チャネル（複数チャネル非対応） | 未対応 |
| Ruby | デフォルト有効（`v2.30.0`以降） | 単一チャネル（複数チャネル非対応） | 未対応 |
| PHP | デフォルト有効（`v2.0.0`以降） | チャネル数設定非対応 | 未対応 |

一覧をみて、セッション層（Multiplexed Sessions）については6言語すべてでデフォルト有効に揃っている一方、下回りのgRPCチャネル管理には言語ごとの差が残っていることがわかります。それぞれの言語グループにおける特徴は以下の通りです。

### Go / Java

Multiplexed Sessionsはすでに標準で有効になっており、複数チャネルの固定プールとDCPの両方に対応しています。DCPを利用する場合は明示的な設定（オプトイン）で有効化します。なお、JavaでDCPを使わない場合の標準の固定チャネル数は、`v6.105.0`以降でGoogle Cloud向けのチャネル管理拡張（`gRPC-GCP`）がデフォルト有効になったことに伴い、従来の4本から8本へ変更されています。

### Node.js

Multiplexed SessionsとDCPの両方が標準で有効になっており、1チャネルあたり25並行リクエストを閾値として最大10チャネルまで自動でスケールアップします。Regular Sessionsを使っていた以前のバージョンでは、チャネルプールの設定をコードから上書きする際にメソッドごとのチャネル紐付け定義（method affinities）まで忘れずにコピーしないと性能が劣化する注意点がありましたが、Multiplexed Sessionsではセッションとチャネルの紐付け自体が不要になったため、チャネル数や閾値だけをシンプルに変更できるようになりました。

### Python

Pythonのクライアントライブラリには歴史的に4種類のセッションプール実装が用意されており、用途に応じた選択が必要でしたが、`v3.57.0`以降でMultiplexed Sessionsがデフォルト有効になりました。一方で、クライアント内での複数gRPCチャネルプールやDCPには未対応です。

### Ruby / PHP

Multiplexed Sessionsには対応しているものの、クライアントライブラリ側で複数gRPCチャネルのプール設定はサポートされていません。Rubyクライアントは1つのクライアントにつき1本のgRPCチャネル（最大100並行リクエスト）で動作する仕様となっています。そのため、1プロセスあたり100を超える並行トランザクションを扱う場合は、セッション設定を調整するのではなく複数のクライアントインスタンスを作成することが推奨されています。またPHPではgRPC拡張の導入が前提となり、クライアントライブラリでのチャネル数の設定はサポートされていません。

## 現在の構成でも気をつけるべきポイント

最後に、Multiplexed Sessionsが標準となった現在の構成において、開発者が設計・運用時に押さえておくべきポイントを整理します。

### クライアントインスタンスはプロセス単位で使い回す

セッションプールのウォームアップが不要になったとはいえ、クライアントインスタンスを生成する際にはgRPCチャネル（TCP/TLSハンドシェイク）の確立や認証情報の初期化が行われます。リクエストを受け取るたびにクライアントを生成・破棄するような実装にすると、毎回の接続確立コストとリソース消費が発生するため、クライアントはアプリケーション起動時に1度だけ作成してプロセス全体で共有し、終了時にクローズする基本原則は変わりません。

### gRPCチャネルの並行上限とDCPのトレードオフ

セッション枯渇を気にする必要はなくなりましたが、「1本のgRPCチャネルあたり最大100並行リクエスト」というHTTP/2ストリームの上限は引き続き存在します。1インスタンスあたり数百並行のリクエストを処理する高負荷サービスでは、GoやJavaならgRPCチャネル数の拡張やDCPの有効化、PythonやRubyのようにクライアントライブラリが単一チャネル構成の場合はクライアントインスタンスの複数化やワーカープロセス数で並行数を確保する設計を検討します。

ただし、DCPにもトレードオフがあります。負荷上昇に合わせてチャネルを追加する際には新しいgRPCチャネルとTCPコネクションを確立するオーバーヘッドが生じるため、急激なスパイク（バースト）が来る環境でレイテンシを厳しく抑えたい場合には、最初から十分な本数を張っておく固定チャネルプールの方が適しているケースもあります。またJavaでDCPを導入する際は、既存の固定チャネル数指定が残っているとDCPが無効になり固定プールとして動作する仕様である点にも注意します。

### クライアントライブラリのバージョン確認と過去の設定の扱い

ここまで説明したMultiplexed Sessionsの恩恵をそのまま受けるための前提は、各言語のクライアントライブラリがデフォルト有効化以降のバージョンに更新されていることです。数年前のバージョンを固定したまま運用しているプロジェクトでは現在もRegular Sessionsのセッションプールで動いているため、まずは使用中のSDKバージョンを確認することをおすすめします。最新バージョンを利用していれば、過去の記事を参考にして`MinSessions`や`MaxSessions`などのセッションプール設定を新規に追加する必要はありません。

## まとめ

Spannerの接続構成について、過去の課題と現在の仕組みを整理しました。

- 一般的なRDBではTCP接続とセッションが1対1で結びついているのに対し、Spannerでは論理IDである「セッション」と、HTTP/2で多重化通信を行う「gRPCチャネル」が分離されています。
- かつては「1セッション＝同時1トランザクション」の制約からセッションプールのサイズ設計・Keep-Alive・リーク対策が必要でしたが、主要6言語でMultiplexed Sessionsがデフォルト有効になったことで、セッション管理にまつわる運用負荷は大半が解消されました。
- 現在の構成では、クライアントインスタンスを使い回す基本を守りつつ、1チャネルあたり最大100並行というgRPCチャネル側の制約やDynamic Channel Poolingのトレードオフ、各言語のクライアントライブラリのチャネル仕様に合わせて設計できます。

過去の情報と現在の仕様が混在して複雑に見えやすい領域ですが、セッション層とgRPCチャネル層を切り分けて捉えることで、シンプルに見通しよく設計できるようになります。なお、GCEやGKE環境向けに通信経路のフロントエンドプロキシ（GFE）をバイパスしてレイテンシを短縮するDirect Connectivityという機能も提供されており、関心のある方は[Spannerの通信レイテンシを短縮するDirect Connectivityの仕組みと実測検証](https://zenn.dev/google_cloud_jp/articles/80f52aa388bf02)も参考情報としてご覧ください。
