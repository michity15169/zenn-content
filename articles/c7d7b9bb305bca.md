## tl;dr

- Spannerはテーブルをプライマリキー順の範囲である「スプリット（Split）」に区切り、複数サーバーへ分散配置してスケールアウトします。
- データ量の増加時だけでなく、特定キー範囲へのアクセス集中時にも、自動的にスプリット境界（Split Boundary）を追加して別サーバーへ負荷を逃がします。
- 連番キーを避ける理由や親子テーブルのインターリーブも、このスプリットの動作から理解できます。

## はじめに

Spannerは、リレーショナルデータベース（以下、RDB）の構造やトランザクション整合性を保ったまま水平スケールできるデータベースとして紹介されることが多い製品です。一方で、RDBの経験がある方ほど「1つのテーブルに見えるのに、裏側でどうやって複数サーバーへ処理を分散しているのか」「なぜ`1, 2, 3...`の連番プライマリキーが推奨されないのか」と疑問に思われるのではないでしょうか。

本稿では、一般的なRDBと対比しながら、Spannerのスプリット（Split）が分割・再配置される動きをアニメーションで視覚的に解説します。

## 一般的なRDBとSpannerのデータ配置の違い

MySQLやPostgreSQLなどの一般的なRDBでは、原則として1台のプライマリサーバーが全データを保持します。1台の性能限界を超えると、アプリケーション側でキー範囲ごとに接続先DBを振り分ける「シャーディング（水平分割）」を実装・運用しなければならなくなります。

一方で、Spannerでは論理的なテーブルは1つのまま、裏側の複数サーバーが「スプリット（Split）」と呼ばれる単位でデータを分担します[^1]。マニュアルでは、スプリットはプライマリキー順に並んだ連続する行の束（チャンク）であり、その開始キーと終了キーの区切りを「スプリット境界（Split Boundary）」と呼ぶと説明されています[^1]。つまり、テーブルの全行をプライマリキー昇順に一列に並べ、適当な区切り位置で複数の束に分けて別々のサーバー（以降、ノード / Node）に担当させるイメージです。

## スプリットが自動的に分割・再配置される仕組み

データ量が少ない初期状態では、テーブル全体が1つのスプリットに収まり、1台のノードで処理されます[^1]。そこから規模やトラフィックが増えると、Spannerは「データ量（サイズ）」と「アクセス負荷（ロード）」の2つの観点で自動的にスプリットを分割・再配置します[^1][^3]。

サイズが大きくなったときは中間付近のキーで2分割し、データサイズが小さくても特定のキー範囲にアクセスが集中（ホットスポット化）したときは、その行間にスプリット境界を追加して別ノードへ移動させます（負荷ベースのスプリット分割 / Load-based splitting）[^1][^4]。

### 事前分割（Pre-splitting）

負荷検知から自動分割・移動の完了までには数分程度かかるため、空テーブルへの大量初期ロードや大規模イベントのようにアクセスが一気に跳ね上がる場面では、最初の1スプリットが先に飽和することがあります[^3]。このように急激な負荷増加が予測できる場合は、あらかじめ分割点（Split points）を指定して境界を作っておく「事前分割（Pre-splitting）」を使います[^3]。

単調増加キー（左）では、Spannerがスプリットを分割しても、直後の新規`INSERT`は常に最大値側の末尾スプリット（`[3k, ∞)`）へ集中します。そのため、ノードを何台増やしても常に末尾担当の1台だけがホットスポットになり続けます（セカンダリインデックスの先頭列にタイムスタンプを置いた場合も同様です）[^4][^5]。

一方で、キーの先頭部分がばらける分散キー（右）にすれば、すべてのスプリットへ同時に書き込みが振り分けられます。代表的な分散手法は以下の通りです[^5]。

- UUID v4（`NEW_UUID()`関数など）を主キーに使う
- ビット反転シーケンス（`bit_reversed_positive`）を使う（Spannerの`IDENTITY`列や`AUTO_INCREMENT` / `SERIAL`も内部でこの方式を使います[^8]）
- 複合キーの先頭に`UserId`やハッシュ値などばらつきのある列を置き、2列目にタイムスタンプを置く（`PRIMARY KEY (UserId, LastAccess)`）

## 関連する複数テーブルを同じスプリットに同居させる（インターリーブ）

スプリットが別々のノードに分散されると、複数テーブルをまたぐ読み書きでサーバー間通信や2フェーズコミット（2PC）が発生しやすくなります[^1][^2]。そこで、頻繁に結合・同時更新する親子テーブル（例: `Singers`と`Albums`）を同じスプリット内に物理的に並べて格納する仕組みが「インターリーブ（`INTERLEAVE IN PARENT`）」です[^1][^6]。

```sql:schema.sql
CREATE TABLE Singers (
  SingerId   INT64 NOT NULL,
  FirstName  STRING(1024),
  LastName   STRING(1024),
) PRIMARY KEY (SingerId);

CREATE TABLE Albums (
  SingerId     INT64 NOT NULL,
  AlbumId      INT64 NOT NULL,
  AlbumTitle   STRING(MAX),
) PRIMARY KEY (SingerId, AlbumId),
  INTERLEAVE IN PARENT Singers ON DELETE CASCADE;
```

子テーブルの主キー先頭に親の主キーを含めて`INTERLEAVE IN PARENT`を宣言すると、スプリット内では親行の直下に子行が並んで格納されます[^1]。

## 自動分割で解消できないホットスポットを見分けるには

普段の運用でスプリットの境界位置を意識する必要はありませんが、自動分割だけでは解消できないホットスポットが発生していないかは、Google Cloudコンソールの「Hotspot insights」やシステム統計ビュー`SPANNER_SYS.SPLIT_STATS_TOP_MINUTE`で確認できます[^4][^7]。

```sql:check_hot_splits.sql
SELECT INTERVAL_END, SPLIT_START, SPLIT_LIMIT, CPU_USAGE_SCORE, AFFECTED_TABLES, UNSPLITTABLE_REASONS
FROM SPANNER_SYS.SPLIT_STATS_TOP_MINUTE
ORDER BY INTERVAL_END DESC, CPU_USAGE_SCORE DESC LIMIT 10;
```

`CPU_USAGE_SCORE`が100%でも数分で収まり`UNSPLITTABLE_REASONS`が空（`[]`）であれば、自動分割と再配置によって正常に解消されています[^4][^7]。一方、10分以上100%が続き以下の理由が記録されている場合は、自動分割だけでは解消できないアクセスパターンのためスキーマやクエリーの見直しが必要です[^4][^7]。

| `UNSPLITTABLE_REASONS` | 状態 | 主な原因と対処 |
| :--- | :--- | :--- |
| `[]`（空配列） | 分割で解消可能／一時的負荷 | 自動分割の進行中または短期スパイク。10分以内に収まれば対応不要[^4][^7] |
| `MOVING_HOT_SPOT` | 高負荷範囲が移動し続けている | 連番・時刻先頭キーへの追記や連続読み取り。UUIDやビット反転等の分散キーへ変更[^4] |
| `HOT_ROW` | 単一1行に負荷が集中 | 最小単位（1行）のため分割不可。シャード分割やキャッシュを検討[^4] |
| `UNISOLATABLE_HOT_ROW` | 隣接する狭い範囲に負荷が集中 | 共通プレフィックス行への集中等で分割点を作れない状態。特定キーへの集中を緩和[^4] |
| `LARGE_SCAN_HOT_SPOT` | 広範囲スキャンによる高負荷 | 細分化するとスキャン性能が落ちるため分割が抑制される。インデックス追加等でスキャン行数を削減[^4] |

## まとめ

Spannerはデータをプライマリキー順のスプリットに分け、サイズや負荷に応じて自動的に境界を追加・移動させることで水平スケールを実現しています。この「キー範囲ごとに分割して別ノードへ逃がす」という動きをイメージしておくと、分散キーの選択やインターリーブ、Pre-splittingといった設計・運用の判断がそのままつながります。
