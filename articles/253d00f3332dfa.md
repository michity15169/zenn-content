## tl;dr

- AntigravityとGemini 4 Hydrogenを使い、ISUCON過去問5題（ISUCON 14 / 13 / 12予選 / 11本選 / 11予選、移植対象はすべてGo実装のみ）をMySQL/SQLiteからSpannerへ自律的に移植（Phase 1）およびパフォーマンスチューニング（Phase 2）させました
- Phase 1（初期移植＋ベンチマーク合格確認）の所要時間は1問あたり約18〜36分、APIコストは\$1.00〜\$2.01（5問合計で\$7.41）でした
- 移植に際して書き換わった元コードの行数は、5問合計9,106行のうち335行（全体の3.7%）でした。さらにベンチマーク用の初期化処理（`POST /initialize`）やDB接続設定を除いたAPIハンドラーのSQL変更に限れば、全体の0.5%〜4.0%（5問合計で`+66 / -134`行）のみで完結しました
- Phase 2（パフォーマンスチューニング）では、エージェントが`SPANNER_SYS`統計からボトルネックを特定し、Batch Mutation（1-RPC化）やキャッシュを段階的に適用して1問あたり\$1.70〜\$4.30でスコアを10倍〜264倍に引き上げました

## はじめに

Spannerは機能拡充が進み、Repeatable Read分離レベルや`SELECT ... FOR UPDATE`、`GENERATED BY DEFAULT AS IDENTITY (BIT_REVERSED_POSITIVE)`、Goの`database/sql`ドライバーである`github.com/googleapis/go-sql-spanner`が揃っています。同時に、先日一般公開されたGemini 4 Hydrogenとエージェント開発環境のAntigravityによって、コード修正からベンチマーカーの実行・検証までを自律的に回せるようになりました。

本記事では、ISUCON過去問5題（Go実装）を題材に、MySQL/SQLiteアプリケーションをSpannerへ移植する際のコスト・実際のコード変更割合・プロンプト、およびチューニングの勘所をまとめます。

## 検証条件と与えたプロンプト

### Phase 1 / Phase 2の定義と検証環境

今回の検証では、移植対象をすべてGo言語の参照実装のみに統一し、作業を以下の2フェーズに分離して計測しました。

- Phase 1（初期移植）：インメモリキャッシュ導入などの最適化は行わず、最小限のコード差分でMySQL/SQLiteからSpannerへ移植し、公式ベンチマーカーで`pass=true`（整合性チェック合格）を確認するフェーズ
- Phase 2（パフォーマンスチューニング）：Phase 1のコミットをベースに、`SPANNER_SYS`の分析やスキーマ・クエリー・アプリケーション層の改善を3〜5サイクル実施してスコアを伸ばすフェーズ

検証環境は`asia-northeast1`の単一マシン（8 vCPU / 31 GiB RAM）とSpannerインスタンス（`1000 PU`）です。

:::message
MySQL/SQLiteとSpannerではデータベースの条件がまったく異なり、コンピューティング環境もコンテスト当時とは異なるため、本記事のベンチマークスコアはPhase 1とPhase 2の相対的な変化を見るための参考程度としてご覧ください。
:::

### Phase 1（初期移植）のプロンプト

最小差分で移植させるため、`go-sql-spanner`とRepeatable Readの採用、およびタイムアウト制限が厳しい`POST /initialize`の実装方針を指定しました。

```markdown
## タスク: MySQL/SQLiteアプリケーションのSpannerへの最小変更移植（Phase 1）

対象ディレクトリのGoアプリケーション（`webapp/go`）を、最小限のコード変更でSpanner上で動作するように移植し、公式ベンチマーカーを実行して`pass=true`を確認してください。

### 接続先情報
- Spanner Database: `projects/<PROJECT_ID>/instances/<INSTANCE_ID>/databases/<DB_ID>`

### Phase 1（初期移植）の設計方針
1. データベースドライバーと分離レベル:
   - `github.com/googleapis/go-sql-spanner`を導入し、既存の`jmoiron/sqlx`のコード構造と`?` / `:named`プレースホルダーをそのまま維持すること。
   - DSNに`isolationLevel=REPEATABLE_READ`を指定し、`SELECT ... FOR UPDATE`を維持すること（未サポートの`FOR SHARE`のみ削除）。
2. スキーマ（DDL）の移行:
   - `webapp/sql/spanner_schema.sql`を作成してSpannerに適用すること。
   - `AUTO_INCREMENT`には`INT64 NOT NULL GENERATED BY DEFAULT AS IDENTITY (BIT_REVERSED_POSITIVE)`を使用すること。
   - Pretest通過に必要なセカンダリインデックスを作成すること。
3. SQL方言の最小置換:
   - `INSERT ... ON DUPLICATE KEY UPDATE` ➔ `INSERT OR UPDATE INTO ...`
   - `INSERT IGNORE INTO` ➔ `INSERT OR IGNORE INTO`
   - `LastInsertId()`を使う`INSERT`文 ➔ 末尾に`THEN RETURN id`を付与して取得
   - MySQLの重複エラー判定（`1062`） ➔ Spannerの`AlreadyExists`判定へ置換
4. `POST /initialize`の高速化:
   - `POST /initialize`内で毎回DDLを実行したり外部CLIスクリプトを呼んだりせず、初期データの事前ロード＋増分削除、または`spanner.Delete(table, spanner.AllKeys())`＋バッチMutationで数秒以内に初期化を完了させること。
5. 完了条件:
   - パフォーマンス目的のキャッシュ導入等は行わず、`pass=true`を確認したら`git commit`して差分とスコアを報告すること。
```

### Phase 2（パフォーマンスチューニング）のプロンプト

```markdown
## タスク: Spanner上でのパフォーマンスチューニング（Phase 2）

現在のPhase 1コミットをベースとして、Spanner上でのベンチマークスコアを最大化するためのチューニングを3〜5サイクル実施してください。

### 方針
- 手法の制限なし:
  - `SPANNER_SYS.QUERY_STATS_TOP_MINUTE`や`TXN_STATS_TOP_MINUTE`を用いたボトルネック分析
  - カバリングインデックス（`STORING`句）の追加、または不要なセカンダリインデックスの削除
  - N+1クエリーの解消、読み取り専用ハンドラーのSingle-Use Read-Only化
  - Native Spanner Client（`cloud.google.com/go/spanner`）のBatch Mutation（`spannerClient.Apply`による1-RPC書き込み）の活用
  - アプリケーション層のインメモリキャッシュや非同期バッチフラッシャーの導入
- 制約:
  - 各サイクルでベンチマーカーを実行して`pass=true`を維持し、スコア推移と効いた施策を記録・コミットすること。
```

## MySQLからSpannerへの移植で実際に書き換わるポイント

Phase 1で実際に書き換わった箇所を5つのパターンに分けて示します。

### 1. ドライバー差し替えとRepeatable Readによるロック構文の維持

`github.com/googleapis/go-sql-spanner`を使い、DSNに`isolationLevel=REPEATABLE_READ`を指定するだけで、既存の`jmoiron/sqlx`のコード、`?`プレースホルダー、および`SELECT ... FOR UPDATE`がそのまま動作します。

ロック周りで唯一変更が必要だったのは、Spannerがサポートしていない`FOR SHARE`の削除のみです（Repeatable Readではトランザクション開始時のスナップショット読み取りが保証されるため、削除するだけで同等の挙動になります）。

```diff:ISUCON 11本選（isucholar）およびISUCON 14（isuride）
- if err := tx.Get(&course, "SELECT * FROM `courses` WHERE `id` = ? FOR SHARE", courseID); err != nil {
+ if err := tx.Get(&course, "SELECT * FROM `courses` WHERE `id` = ?", courseID); err != nil {
```

### 2. AUTO_INCREMENTとLastInsertId()の置き換え

MySQLの`AUTO_INCREMENT`は、書き込みホットスポットを避けるためDDLで`GENERATED BY DEFAULT AS IDENTITY (BIT_REVERSED_POSITIVE)`に変換します。これに伴いアプリ側で変わるのは以下の2点です。

- `LastInsertId()`の置換：Spannerドライバーでは`LastInsertId()`が使えないため、`INSERT`文の末尾に`THEN RETURN id`を付与して`GetContext`等で受け取ります。
- `ORDER BY id DESC`の修正：`BIT_REVERSED_POSITIVE`のIDは作成順に並ばないため、新着順を意図した`ORDER BY id DESC`は`ORDER BY created_at DESC, id DESC`に修正します。

```diff:ISUCON 13（isupipe）とISUCON 11予選（isucondition）
- res, err := tx.NamedExecContext(ctx, "INSERT INTO users (...) VALUES (...)", &user)
- userID, err := res.LastInsertId()
+ var userID int64
+ err := tx.GetContext(ctx, &userID, "INSERT INTO users (...) VALUES (?, ?, ?, ?) THEN RETURN id", ...)

- "SELECT * FROM `isu` WHERE `jia_user_id` = ? ORDER BY `id` DESC"
+ "SELECT * FROM `isu` WHERE `jia_user_id` = ? ORDER BY `created_at` DESC, `id` DESC"
```

### 3. Upsert・Ignore・重複エラー判定とSQL関数の置換

UpsertやIgnore構文、重複エラー判定、およびMySQL固有の関数は機械的に置換できます。

| 分類 | MySQLでの記述 | Spanner（GoogleSQL）での記述 | 該当問題 |
| :--- | :--- | :--- | :--- |
| Upsert | `INSERT ... ON DUPLICATE KEY UPDATE ...` | `INSERT OR UPDATE INTO ...` | 12予選, 11本選, 11予選 |
| Ignore | `INSERT IGNORE INTO ...` | `INSERT OR IGNORE INTO ...` | 11予選 |
| 重複エラー判定 | `mysqlErr.Number == 1062` | `strings.Contains(err.Error(), "AlreadyExists")` | 12予選, 11本選, 11予選 |
| 更新タイムスタンプ | DDLの`ON UPDATE CURRENT_TIMESTAMP` | `UPDATE ... SET updated_at = CURRENT_TIMESTAMP()` | 14 |
| ミリ秒UNIX時刻 | `FLOOR(UNIX_TIMESTAMP(NOW(3))*1000)` | `UNIX_MILLIS(CURRENT_TIMESTAMP())` | 14 |
| ランダム1件取得 | `ORDER BY RAND() LIMIT 1` | `ORDER BY GENERATE_UUID() LIMIT 1` | 14 |
| JOIN付きUPDATE | `UPDATE submissions JOIN users ON ...` | `WHERE user_id = (SELECT id FROM users WHERE ...)` | 11本選 |
| ウィンドウ関数`LAG` | `LAG(latitude) OVER (PARTITION BY ...)` | `ARRAY_AGG(STRUCT(...))`＋`UNNEST`で隣接差分を集計 | 14 |

### 4. テナント別SQLite 100個の単一Spanner DBへの統合（ISUCON 12予選）

管理用MySQLと100個のテナント別SQLiteファイル（`1.db`〜`100.db`）を使うISUCON 12予選（isuports）も、元テーブルに`tenant_id`カラムが含まれているため、全テーブルを単一のSpanner DBに統合できました。`connectToTenantDB`が共有の`adminDB`をラップした構造体（`Close()`をno-op化）を返すようにしたことで、ハンドラー側の`tenantDB`呼び出しを1行も変えずに移行できています。

```go:ISUCON 12予選（isuports）isuports.go
type tenantDBWrapper struct{ *sqlx.DB }

func (tenantDBWrapper) Close() error { return nil }

func connectToTenantDB(id int64) (tenantDBWrapper, error) {
	return tenantDBWrapper{adminDB}, nil
}
```

### 5. POST /initializeの高速リセット

SpannerではDDLの実行に数秒〜数十秒かかるため、ベンチマーク開始時の`POST /initialize`ではテーブルを再作成せずデータのみをリセットします。

- 数千〜数万行規模（ISUCON 14 / 13 / 11本選 / 11予選）：`spanner.Delete(table, spanner.AllKeys())`と並列Batch Mutation（`spannerClient.Apply`）で0.5〜1.5秒で初期データを再投入
- 約695万行規模（ISUCON 12予選）：初期データのタイムスタンプ（`created_at < 1654041600`）より後に追加・更新されたレコードのみを`DELETE` / `UPDATE`する差分リセットで約2秒に短縮

## パフォーマンスチューニング（Phase 2）でエージェントがやったこと

各問題のサイクル別スコア推移と、エージェントが自律的に行った主な改善アプローチは以下の通りです。

| 題材 | Phase 1 | Cycle 1 | Cycle 2 | Cycle 3 | Cycle 4 | Cycle 5 | 最終倍率 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| ISUCON 14 (`isuride`) | 3,236 | 6,485 | 6,883 | 10,126 | 812,435 | 856,975 | 264.8x |
| ISUCON 13 (`isupipe`) | 8,423 | 59,123 | 61,746 | 186,550 | 191,091 | - | 22.7x |
| ISUCON 12予選 (`isuports`) | 2,209 | 40,933 | 25,439 | 138,113 | 210,088 | - | 95.1x |
| ISUCON 11本選 (`isucholar`) | 31,879 | 49,237 | 58,369 | 150,783 | 320,684 | - | 10.1x |
| ISUCON 11予選 (`isucondition`) | 14,120 | 15,196 | 22,020 | 15,518 | 228,666 | 318,377 | 22.5x |

- `SPANNER_SYS`を起点にしたN+1と長大トランザクションの特定：ローカルのMySQL/SQLiteでは目立たないN+1も、ネットワーク越しのSpannerでは1 RPCあたり0.2〜0.5msのRTTが積み重なります。すべてのエージェントがCycle 1で`SPANNER_SYS.QUERY_STATS_TOP_MINUTE`と`TXN_STATS_TOP_MINUTE`をクエリーし、1分間に6万〜13万回呼ばれていたPoint Lookupのバッチ化・キャッシュ化や、`FOR UPDATE`トランザクション内で53回OSプロセス（`cp`/`zip`）をforkして平均891msロックを保持していた処理（ISUCON 11本選）のオンメモリ化を行っていました。
- カバリングインデックス（`STORING`句）と不要インデックスの削除：参照時のBack-joinを避ける`STORING`句の追加（ISUCON 11予選・11本選）に加え、ISUCON 14ではインメモリ化に伴い不要になった14個のセカンダリインデックスを削除することで、分散Writeのオーバーヘッドとユニークインデックス競合を同時に解消していました（Cycle 4で`10,126 ➔ 812,435`）。
- Single-Use Read-Only化とMutation（`Apply`）による1-RPC化：元コードで`GET`ハンドラーが開始していた不要なRead-Writeトランザクションを除去した上で、書き込み系を`database/sql`のDML＋Commit（複数RPC）からNative Spanner Clientの`spannerClient.Apply`（1-RPC Mutation）へ統一していました。特にISUCON 13のCycle 3（`61,746 ➔ 186,550`）では、`reservation_slots`の2カラム範囲条件`FOR UPDATE`が引き起こしていた約8,000行の排他ロック競合を、主キー指定の`spanner.Update`＋`InsertOrUpdate`の1-RPC適用で解消しています。
- スコア低下からの自己診断（ISUCON 11予選）：Cycle 2で非同期バッチフラッシャーを入れた後、Cycle 3で一度スコアが低下（`22,020 ➔ 15,518`）した際、エージェントはログから「フラッシャーの無制限並列実行によるSpannerロック競合」と「非同期フラッシュ前のSpanner読み取りによるRead-Your-Writes遅延」を自ら突き止め、Cycle 4でSingle-Flightフラッシャー＋メモリ上の時系列スライス参照に改修して`228,666`点（最終的に`318,377`点）へ伸ばしていました。

## まとめ

SpannerのRepeatable Readや`go-sql-spanner`が整った現在、MySQL/SQLiteアプリケーションの移植で書き換える必要があるコードは元コード全体の数%（APIハンドラーのSQLに限れば0.5%〜4.0%程度）に収まります。そこにAntigravityとGemini 4 Hydrogenを組み合わせることで、1問あたり約20〜35分・\$1〜\$2で初期移植とベンチマーク合格まで到達でき、その後の`SPANNER_SYS`を活用したパフォーマンスチューニングまで含めても1問あたり\$3.4〜\$5.5程度（5問合計\$21.45）で一気通貫に実行できました。

最後に、これほど多様なアーキテクチャーの課題と精巧なベンチマーカーをオープンに公開・維持してくださっているISUCONプロジェクトおよび運営・作問関係者の皆様に深く感謝いたします。実践的なベンチマーク環境が公開されているおかげで、データベースの進化やAIエージェントの実力を定量的に検証することができました。
