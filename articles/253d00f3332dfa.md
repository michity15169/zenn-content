## tl;dr

- ISUCON過去問5題（Go実装）のSpannerへの初期移植は、1問あたり約18〜36分・\$1.00〜\$2.01で完了しました。
- 移植時に書き換わった元コードは全体の3.7%（APIハンドラーのSQL変更に限れば0.5%〜4.0%）にとどまります。
- 続くパフォーマンスチューニングでは、全5題でテーブルのインターリーブを含む最適化が行われ、1問あたり\$3.70〜\$8.65でスコアが約14倍〜226倍に向上しました。

## はじめに

Spannerは機能拡充が進み、MySQLでも馴染みのあるRepeatable Read分離レベルや`SELECT ... FOR UPDATE`、`AUTO_INCREMENT`に相当する`IDENTITY`列、Goの`database/sql`ドライバーである`github.com/googleapis/go-sql-spanner`が揃っています。同時に、2026年11月に一般公開されたGemini 4 Hydrogenとエージェント開発環境のAntigravityによって、コード修正からベンチマーカーの実行・検証までを自律的に回せるようになりました。

本稿では、ISUCON過去問5題（Go実装）を題材に、MySQL/SQLiteアプリケーションをSpannerへ移植する際のコスト・実際のコード変更割合・プロンプト、およびチューニングの勘所をまとめます。

## 検証条件と与えたプロンプト

### Phase 1 / Phase 2の定義と検証環境

今回の検証では、移植対象をすべてGo言語の参照実装のみに統一し、作業を以下の2フェーズに分離して計測しました。

- Phase 1（初期移植）：インメモリキャッシュ導入などの最適化は行わず、最小限のコード差分でMySQL/SQLiteからSpannerへ移植し、公式ベンチマーカーで`pass=true`（整合性チェック合格）を確認するフェーズ
- Phase 2（パフォーマンスチューニング）：Phase 1のコミットをベースに、システム統計テーブル（`SPANNER_SYS`）の分析やスキーマ・クエリー・アプリケーション層の改善を3〜5サイクル実施してスコアを伸ばすフェーズ

検証環境は`asia-northeast1`の単一マシン（8 vCPU / 31 GiB RAM）とSpannerインスタンス（`1,000 PU`＝1ノード相当）です。

:::message
MySQL/SQLiteとSpannerではデータベースの条件がまったく異なり、コンピューティング環境もコンテスト当時とは異なるため、本稿のベンチマークスコアはPhase 1とPhase 2の相対的な変化を見るための参考程度としてご覧ください。
:::

### Phase 1（初期移植）のプロンプト

最小差分で移植させるため、`go-sql-spanner`とRepeatable Readの採用、およびタイムアウト制限が厳しい`POST /initialize`の実装方針を指定しました。

```markdown
## タスク: MySQL/SQLiteアプリケーションのSpannerへの最小変更移植（Phase 1）

対象ディレクトリのGoアプリケーション（`webapp/go`）を、最小限のコード変更でSpanner上で動作するように移植し、公式ベンチマーカーを実行して`pass=true`を確認してください。

### 接続先情報
- Spanner Database: `projects/<PROJECT_ID>/instances/<INSTANCE_ID>/databases/<DB_ID>`

### Phase 1（初期移植）の設計方針
1. データベースドライバーと分離レベル:
   - `github.com/googleapis/go-sql-spanner`を導入し、既存の`jmoiron/sqlx`のコード構造と`?` / `:named`プレースホルダーをそのまま維持すること。
   - DSNに`isolationLevel=REPEATABLE_READ`を指定し、`SELECT ... FOR UPDATE`を維持すること（未サポートの`FOR SHARE`のみ削除）。
2. スキーマ（DDL）の移行:
   - `webapp/sql/spanner_schema.sql`を作成してSpannerに適用すること。
   - `AUTO_INCREMENT`には`INT64 NOT NULL GENERATED BY DEFAULT AS IDENTITY (BIT_REVERSED_POSITIVE)`を使用すること。
   - Pretest通過に必要なセカンダリインデックスを作成すること。
3. SQL方言の最小置換:
   - `INSERT ... ON DUPLICATE KEY UPDATE` ➔ `INSERT OR UPDATE INTO ...`
   - `INSERT IGNORE INTO` ➔ `INSERT OR IGNORE INTO`
   - `LastInsertId()`を使う`INSERT`文 ➔ 末尾に`THEN RETURN id`を付与して取得
   - MySQLの重複エラー判定（`1062`） ➔ Spannerの`AlreadyExists`判定へ置換
4. `POST /initialize`の高速化:
   - `POST /initialize`内で毎回DDLを実行したり外部CLIスクリプトを呼んだりせず、初期データの事前ロード＋増分削除、または`spanner.Delete(table, spanner.AllKeys())`＋バッチMutationで数秒以内に初期化を完了させること。
5. 完了条件:
   - パフォーマンス目的のキャッシュ導入等は行わず、`pass=true`を確認したら`git commit`して差分とスコアを報告すること。
```

### Phase 2（パフォーマンスチューニング）のプロンプト

```markdown
## タスク: Spanner上でのパフォーマンスチューニング（Phase 2）

現在のPhase 1コミットをベースとして、Spanner上でのベンチマークスコアを最大化するためのチューニングを3〜5サイクル実施してください。

### 方針
- 手法の制限なし:
  - `SPANNER_SYS.QUERY_STATS_TOP_MINUTE`や`TXN_STATS_TOP_MINUTE`、`LOCK_STATS_TOP_MINUTE`を用いたボトルネック分析
  - 親子関係にあるテーブルのインターリーブ（複合主キー化＋`INTERLEAVE IN PARENT`または`INTERLEAVE IN`）によるデータ局所性の改善
  - カバリングインデックス（`STORING`句）の追加、または不要なセカンダリインデックスの削除
  - N+1クエリーの解消、読み取り専用ハンドラーのSingle-Use Read-Only化
  - Native Spanner Client（`cloud.google.com/go/spanner`）のBatch Mutation（`spannerClient.Apply`による1-RPC書き込み）の活用
  - アプリケーション層のインメモリキャッシュや非同期バッチフラッシャーの導入
- 制約:
  - 各サイクルでベンチマーカーを実行して`pass=true`を維持し、スコア推移と効いた施策を記録・コミットすること。
```

## MySQLからSpannerへの移植で実際に書き換わるポイント

Phase 1で実際に書き換わった主な箇所を整理します。

### ドライバー差し替えとRepeatable Readによるロック構文の維持

`github.com/googleapis/go-sql-spanner`を使い、DSNに`;isolationLevel=REPEATABLE_READ`を指定するだけで、既存の`jmoiron/sqlx`のコード、`?`プレースホルダー、および`SELECT ... FOR UPDATE`がそのまま動作します。

ロック周りで変更が必要だったのは、読み取り行に共有ロックをかけて他トランザクションからの更新を防ぐMySQLの`FOR SHARE`のみです。Spannerは`FOR SHARE`をサポートしていないため、今回の5題では削除のみで整合性チェックを通過しました。ただし、Repeatable Readの通常`SELECT`はロックを取得せず並行更新も検証しないため、読み取り行の変更も防ぐ必要がある箇所では排他ロックの`FOR UPDATE`へ置き換えます。

```diff go:isucon11-final/webapp/go/main.go
- if err := tx.Get(&course, "SELECT * FROM `courses` WHERE `id` = ? FOR SHARE", courseID); err != nil {
+ if err := tx.Get(&course, "SELECT * FROM `courses` WHERE `id` = ?", courseID); err != nil {
```

### AUTO_INCREMENTとLastInsertId()への対応

MySQLの`AUTO_INCREMENT`は、書き込みホットスポットを避けるためDDLで`GENERATED BY DEFAULT AS IDENTITY (BIT_REVERSED_POSITIVE)`に変換します。アプリケーション側では、`LastInsertId()`を使う`INSERT`文の末尾に`THEN RETURN id`を付与するだけで既存の`ExecContext` / `NamedExecContext`と`LastInsertId()`がそのまま動作します。一方、`BIT_REVERSED_POSITIVE`のIDは作成順に並ばないため、新着順を意図した`ORDER BY id DESC`は`ORDER BY created_at DESC, id DESC`に修正します。

```diff go
// ISUCON 13（isupipe）: user_handler.go
- result, err := tx.NamedExecContext(ctx, "INSERT INTO users (...) VALUES(:name, ...)", userModel)
+ result, err := tx.NamedExecContext(ctx, "INSERT INTO users (...) VALUES(:name, ...) THEN RETURN id", userModel)
  // 既存の result.LastInsertId() がそのまま動作する

// ISUCON 11予選（isucondition）: main.go
- "SELECT * FROM `isu` WHERE `jia_user_id` = ? ORDER BY `id` DESC"
+ "SELECT * FROM `isu` WHERE `jia_user_id` = ? ORDER BY `created_at` DESC, `id` DESC"
```

### Upsert・Ignore・重複エラー判定とSQL関数の置換

今回の題材におけるUpsertやIgnore構文、重複エラー判定、およびMySQL固有の関数は以下の通り置換しました。なお、`INSERT OR UPDATE` / `INSERT OR IGNORE`は主キー重複の単純上書き・スキップ専用のため、ユニークインデックス競合や加算更新を伴う場合は`ON CONFLICT`句を使います。

| 分類 | MySQLでの記述 | Spanner（GoogleSQL）での記述 | 該当問題 |
| :--- | :--- | :--- | :--- |
| Upsert | `INSERT ... ON DUPLICATE KEY UPDATE ...` | `INSERT OR UPDATE INTO ...` | 12予選, 11本選, 11予選 |
| Ignore | `INSERT IGNORE INTO ...` | `INSERT OR IGNORE INTO ...` | 11予選 |
| 重複エラー判定 | `mysqlErr.Number == 1062` | `status.Code(err) == codes.AlreadyExists`など | 12予選, 11本選, 11予選 |
| 更新タイムスタンプ | DDLの`ON UPDATE CURRENT_TIMESTAMP` | DMLで`SET updated_at = CURRENT_TIMESTAMP()`[^3] | 14 |
| ミリ秒UNIX時刻 | `FLOOR(UNIX_TIMESTAMP(NOW(3))*1000)` | `UNIX_MILLIS(CURRENT_TIMESTAMP())` | 14 |
| ランダム1件取得 | `ORDER BY RAND() LIMIT 1` | `ORDER BY GENERATE_UUID() LIMIT 1` | 14 |
| JOIN付きUPDATE | `UPDATE submissions JOIN users ON ...` | `WHERE user_id = (SELECT id FROM users WHERE ...)` | 11本選 |
| ウィンドウ関数`LAG` | `LAG(latitude) OVER (PARTITION BY ...)` | `ARRAY_AGG(STRUCT(...))`＋`UNNEST`で隣接差分を集計 | 14 |

### テナント別SQLite 100個の単一Spanner DBへの統合（ISUCON 12予選）

管理用MySQLと100個のテナント別SQLiteファイル（`1.db`〜`100.db`）を使うISUCON 12予選（isuports）も、元テーブルに`tenant_id`カラムが含まれているため、全テーブルを単一のSpanner DBに統合できました。`connectToTenantDB`が共有の`adminDB`をラップした構造体（`Close()`をno-op化）を返すようにしたことで、ハンドラー側の`tenantDB`呼び出しを1行も変えずに移行できています。

```go:isucon12-qualify/webapp/go/isuports.go
type tenantDBWrapper struct{ *sqlx.DB }

func (tenantDBWrapper) Close() error { return nil }

func connectToTenantDB(id int64) (tenantDBWrapper, error) {
	return tenantDBWrapper{adminDB}, nil
}
```

### POST /initializeの高速リセット

SpannerではDDLの実行に数秒〜数十秒かかるため、ベンチマーク開始時の`POST /initialize`ではテーブルを再作成せずデータのみをリセットします。数千〜数万行規模の4題（ISUCON 14 / 13 / 11本選 / 11予選）では、`spanner.Delete(table, spanner.AllKeys())`と並列Batch Mutation（`spannerClient.Apply`）で初期データを再投入し、0.5〜1.5秒で完了させました。一方、約695万行あるISUCON 12予選では、初期データのタイムスタンプ（`created_at < 1654041600`）より後に追加・更新されたレコードのみを`DELETE` / `UPDATE`する差分リセットで約2秒に短縮しています。

### 親子テーブルのインターリーブ（INTERLEAVE IN PARENT）と主キー再設計

全5題ともCycle 1でデータの親子関係とアクセスパターンを分析し、`INTERLEAVE IN PARENT ... ON DELETE CASCADE`を導入しました。たとえばISUCON 12予選では`tenant`配下に`player`と`competition`、さらに`competition`配下に`player_score`と`visit_history`を置く3階層に再構成し、カスケード削除によってPhase 1でホットスポットになっていた単調増加タイムスタンプのインデックス5本も撤去しています。ISUCON 11本選では`courses`配下3テーブルと`users`配下の`unread_announcements`をインターリーブする一方、親キーなしで単体参照される`announcements`はトップレベルに残す使い分けも行われました。

またISUCON 13では、`livestreams`配下に6つの子テーブルをインターリーブした結果、親テーブル単体の`ORDER BY livestream_id DESC LIMIT 50`が物理的に挟まった子テーブル行を跨いでスキャンし、`avg_rows_scanned`が7,821行へ増える現象を`SPANNER_SYS`から検知して降順カバリングインデックスで50行スキャン（0.93ms）へ解消しています。

### SPANNER_SYSを起点にしたN+1とトランザクション内I/Oの解消

ローカルのMySQL/SQLiteでは目立たないN+1も、ネットワーク越しのSpannerではgRPCのRTTが積み重なります。各エージェントは`SPANNER_SYS`の`QUERY_STATS_TOP_MINUTE`・`TXN_STATS_TOP_MINUTE`・`LOCK_STATS_TOP_MINUTE`からボトルネックを特定し、毎分数万〜十数万回呼ばれていたPoint Lookupの`UNNEST`バッチ取得化やキャッシュ化を実施しました。トランザクション内の外部I/Oも解消されており、ISUCON 11本選では外部コマンド（`cp`/`zip`）を50回起動して平均674ms保持していた処理をインメモリの`archive/zip`へ、ISUCON 14ではトランザクション内の決済HTTPリトライ（平均160ms）を`Idempotency-Key`付きのトランザクション外呼び出しへ分離しています。

### Single-Use Read-Only化とMutation（Apply）による1-RPC・バッチ化

元コードで`GET`ハンドラーが開始していた不要なRead-WriteトランザクションをロックレスのSingle-Use Read-Only（`spannerClient.Single()`）へ置き換え、書き込み系はDML＋Commit（複数RPC）から`spannerClient.Apply`（1-RPC Mutation）と非同期バッチフラッシャー（Group Commit / Coalescing）へ移行しました。インターリーブによるスプリット局所化とも組み合わさり、複数テーブルへの書き込みでも2フェーズコミットを伴わない単一スプリット処理（`avg_participants = 1.0`）を達成しています。

### カバリングインデックス（STORING句）と不要インデックスの段階的削除

序盤サイクルではテーブル本体への再参照（Back-join）を防ぐ`STORING`句やインターリーブインデックス（`INTERLEAVE IN`）を追加し、後半サイクルで読み取り層のインメモリキャッシュ化が進むと、書き込み増幅（Write Amplification）の要因になっていたセカンダリインデックス群を`DROP INDEX`で削除する段階的な判断も行われました。たとえばISUCON 12予選では不要インデックス3本の削除と1-RPC `Apply`化により、`player_score`バッチ書き込みの平均レイテンシが175.3msから6.5msへ低下しています。

## まとめ

SpannerのRepeatable Readや`go-sql-spanner`が整った現在、MySQL/SQLiteアプリケーションの移植で書き換える必要があるコードは元コード全体の数%（APIハンドラーのSQLに限れば0.5%〜4.0%程度）に収まります。そこにAntigravityとGemini 4 Hydrogenを組み合わせることで、1問あたり約20〜35分・\$1〜\$2で初期移植とベンチマーク合格まで到達でき、その後のインターリーブ設計や`SPANNER_SYS`分析を含むパフォーマンスチューニングまで通しても1問あたり\$5.5〜\$9.8程度（5問合計\$37.61）で実行できました。

最後に、これほど多様なアーキテクチャの課題と精巧なベンチマーカーをオープンに公開・維持してくださっているISUCONプロジェクトおよび運営・作問関係者の皆様に深く感謝いたします。実践的なベンチマーク環境が公開されているおかげで、データベースの進化やAIエージェントの実力を定量的に検証することができました。
